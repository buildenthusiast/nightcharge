# Падащо меню с марки инвертори — проучване

Дата: 2026-10-13. Само проучване, без промени в кода.

**Важно:** част от информацията за запис е от публично известни интеграции (Home Assistant, библиотеки с отворен код), а не от официалната документация. Потвърждава се след регистрация като разработчик при всяка марка.

## 1. Марки за падащото меню

| Марка | Облачно API | Четене | Запис на схема за зареждане | Локално | Статус в менюто |
|---|---|---|---|---|---|
| **Deye** | Deye Cloud Developer API (EU) | Да, вече работи в приложението | Да се провери в документацията | Modbus | Работи (четене) |
| **Growatt** | OpenAPI V1 и неофициално ShineServer API | Да | Да през неофициалното API (HA има `update_time_segment`) | Modbus / Shine Wi-Fi | Втора вълна, рисков неофициален API |
| **Victron** | VRM Public API | Да, документирано | Да, през VRM / Venus OS (Dynamic ESS), нужен GX | MQTT / Modbus | Тестова марка |
| **Solis** | SolisCloud API (подписани заявки) | Да | Да, има time charging, управлявано и през API | Modbus | Втора вълна |
| **Sungrow** | iSolarCloud Open API | Да | Възможно, зависи от модела | Modbus | Втора вълна |
| **Huawei** | FusionSolar Northbound API | Да | Да, но достъпът е за партньори | Modbus | Скрито, докато има достъп |
| **GoodWe** | SEMS (неофициално) | Да, неофициално | Неясно | Modbus / UDP | Скрито, нестабилно |
| **SolarEdge** | Monitoring API | Да | Не (read-only) | Modbus | Само отчети, без запис |
| **Fronius** | Solar API (локален JSON) | Да, локално | Ограничено | HTTP JSON | Само отчети |
| **SMA** | Sunny Portal / ennexOS | Ограничено | Ограничено | Speedwire / Modbus | Скрито (партньорство) |

**Как работи менюто:** потребителят избира марка, приложението показва само полетата, които тя поддържа (например SolarEdge без „запис на схема“), и след това пита за данните за входа от производителя.

## 2. Какво трябва за поддръжка на менюто

1. **Интерфейс `InverterProvider`** с методи `live()`, `history(from, to)`, `discover()`, и по избор `setChargeSchedule(...)`, плюс `capabilities`, по които UI скрива неподдържаните функции.
2. **Нормализиран модел.** Сега `Live`, `Inverter` и `Specs` в `DeyeApi.kt` са специфични за Deye. Трябва да се преместят в общ модел (`core/Models.kt` е почти готов). `Planner.kt` не трябва да знае за марката.
3. **Адаптер за всяка марка:** логин или токен, откриване на станции, четене, по желание запис. Таймаути и обработка на грешки по марка.
4. **Вход на потребителя.** Всеки въвежда собствените си данни от производителя. Без сървър с потребителски пароли, поне на първия етап.
5. **Тайни на телефона.** Android Keystore и `EncryptedSharedPreferences`. Трябва да се провери дали `Store.kt` вече ги пази шифровано.
6. **appId/appSecret.** Ако марката изисква appSecret, той се вкарва в APK-то и може да се извлече. Условията на марката трябва да позволяват това.
7. **Безопасност при запис:** граници за SoC и мощност, потвърждение преди първи запис, лог на записаното и възможност за връщане към предишните настройки.

**Грубо усилие:** рефакторингът с Deye като първи адаптер е около 1–2 седмици. Всяка следваща марка е около 3–7 дни, ако API е стабилно. Неофициалните API изискват поддръжка при промени.

## 3. Препоръка

1. **Deye**: основата, вече работи за четене.
2. **Growatt**: голям дял в България и ЕС, втора марка, с риск от неофициалния API.
3. **Victron**: тестова марка с чист и документиран API.

Huawei, GoodWe и SMA да се добавят по-късно, при партньорски достъп или ясни условия. Solis и Sungrow са добри за следващата вълна след Growatt.
